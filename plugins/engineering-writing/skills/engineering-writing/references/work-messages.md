# Engineering work messages

Give the recipient enough context to understand the point and respond. Apply the shared principles in [the skill entry point](../SKILL.md).

## Put the recipient's need first

Lead with the result, problem, decision, or request. Include the context that explains its significance for this recipient. When action is needed, say who should act, what they should decide or do, and the deadline if one is known.

Prefer specific dates to relative ones when a message may be read later. Preserve the supplied date's precision; a missing year or time zone needs clarification only when it changes the meaning. Keep the urgency proportional to the actual consequence.

Use the tone and conventions of the conversation. A short chat message often needs one paragraph. An email may need a greeting or sign-off. Match the requested voice while keeping the point easy to find.

## Write useful review comments

Name the concrete condition, the behavior it produces, and the consequence. Recommend an action when the evidence supports one, and distinguish a defect from a preference or open question. Keep the comment within what the inspected material establishes.

Illustrative example:

> An empty batch reaches `events[0]` here, which raises an error before the importer returns. Could we return early for an empty batch?

The condition and failing operation explain the request. A claim about a real implementation needs evidence from that implementation.

## Keep the response proportional

Use connected prose for a single point and a list when the recipient needs to compare or answer separate items. Preserve a concrete next action without adding an automatic closing offer. This guidance covers composing the message; sending it belongs to the surrounding task's authorization and tools.
